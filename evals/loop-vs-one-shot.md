## Reading (added by hand after the run, 2026-11-05)

- **The loop resolved one more issue (7/10 vs 6/10) for $0.15 more (+6%) and one more worker call.** The
  difference is ISSUE-006 alone. In both arms the first attempt failed `npm run check:secrets`: the
  worker's new test put a key-shaped value next to the API-key variable name
  (`test/seat-only-guard.test.ts` in the one-shot run). One-shot stops there. The loop passed the
  verifier's evidence back, and attempt 2 went green. That is the case lesson 9.3 asks about: the extra
  complexity paid for itself, but only on issues where the first attempt fails in a way a check can
  explain.
- **On the other 9 issues the two arms behaved the same.** The 6 easy issues were green on the first
  attempt in both arms (similar turns and cost). The 3 issues built to escalate (decision, protected
  path, too big) ended with **no diff** in both: the worker declined in 2–4 turns ($0.12–0.17). Neither
  arm "resolved" them, which is right: a person must decide, edit `test/acceptance/`, or split the work.
- **Where the loop's value really is on this set: not the resolve rate, the handling.** Every non-green
  issue in the loop arm ends with a status, an escalation summary and a branch name. The one-shot arm
  ends with a temp folder that is thrown away. And the loop never ships the red ISSUE-006 change.
- **Small sample, one run per arm.** One issue of difference is within run-to-run noise for a model. The
  honest claim is "the loop recovered the one failure that had machine-readable evidence, at little extra
  cost", not "the loop is 10 points better". Costs are `total_cost_usd` estimates on a Team seat, not a bill.
